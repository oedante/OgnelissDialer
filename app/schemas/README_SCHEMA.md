# Схемы базы данных

## Почему файлы схем обязаны быть в репозитории

Room экспортирует схему каждой версии в JSON. По этим файлам он:

1. **Проверяет миграции в тестах.** `MigrationTestHelper` создаёт базу
   старой версии именно по такому файлу. Без него тест миграций
   не запустится вовсе — а миграция без теста означает риск потерять
   заметки, метки и списки блокировки у пользователей при обновлении.

2. **Предупреждает об изменении схемы без увеличения версии.** Это самая
   частая ошибка разработки: сущность поправили, версию поднять забыли,
   и приложение падает при первом обращении к базе с сообщением
   «Room cannot verify the data integrity».

## Как они появляются

Автоматически при сборке — путь задан в `app/build.gradle.kts`:

```kotlin
ksp { arg("room.schemaLocation", "$projectDir/schemas") }
```

После первой успешной сборки здесь появятся `1.json` и `2.json`.
**Их нужно закоммитить.** Файлы в `.gitignore` не входят намеренно.

## Текущие версии

| Версия | Что добавилось |
|---|---|
| 1 | Заметки, правила блокировки, индекс T9 |
| 2 | Предпочтения SIM по номерам (`sim_preferences`) |
| 3–5 | Причины блокировки, кэш книги, напоминания |
| 6 | Отметки о спаме отдельно от заметок (`spam_marks`) |
| 7 | Имя «Фамилия Имя» в кэше книги (`contact_cache.nameAlt`) |
| 8 | Имена от оператора — «маркировка звонков» (`network_names`, 1.8.0) |

После сборки 1.8.0 здесь появятся `7.json` и `8.json` — их нужно
закоммитить: без них `MigrationTest` не проверит миграции 6 → 7 и 7 → 8.

## При изменении схемы

1. Увеличить `version` в `AppDatabase`
2. Написать `Migration` и добавить в `MIGRATIONS`
3. Собрать проект — появится новый JSON
4. Скопировать шаблон теста из `MigrationTest` и проверить, что данные
   пользователя выжили. Проверка «миграция не упала» недостаточна:
   она проходит и при полном очищении таблиц
