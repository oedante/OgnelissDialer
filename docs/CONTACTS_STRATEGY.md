# Работа с контактами: что делаем сами, что отдаём системе

## Короткий ответ

**Гибрид с перевесом в сторону системного приложения.**
Полный редактор контактов внутри Ogneliss не реализуется.

## Почему не полный редактор

Разрешения тут ни при чём. `WRITE_CONTACTS` уже заявлено и, в отличие
от `CALL_LOG` и `PHONE`, не требует отдельной декларации в Google Play.

Проблема в модели данных `ContactsContract`. Это один из самых сложных
API в Android, и цена ошибки особенная: **мы портим данные, которые живут
вне нашего приложения** и нужны десятку других программ.

### Четыре ловушки

**1. Агрегация.** То, что пользователь видит как один контакт, — склейка
нескольких `RawContacts`: Google, локальный, SIM, плюс свои записи
добавляют WhatsApp, Telegram, Viber. Редактируя контакт, нужно выбрать,
в какой именно raw писать. Ошибка порождает дубли, которые пользователь
потом разбирает руками.

**2. Аккаунты ограничивают набор полей.** Каждый тип аккаунта объявляет
в своих метаданных, какие поля поддерживает. Записанное неподдерживаемое
поле теряется при первой синхронизации — молча, без ошибки. Пользователь
обнаружит пропажу через неделю и не поймёт причину.

**3. Часть raw-записей только для чтения.** Записи мессенджеров править
нельзя. Попытка создаёт мусор либо тихо игнорируется.

**4. Поля сложнее, чем выглядят.** Структурированное имя из шести частей
(включая фонетические), произвольные mimetype, фото в двух вариантах
(миниатюра в `PHOTO` и полноразмерное через `PHOTO_FILE_ID`),
пользовательские метки типов, группы, `AggregationExceptions`.

**5. В какой аккаунт создавать новый контакт?** Если у пользователя есть
Google, Exchange и локальный, выбор неочевиден. Ошибка означает, что
контакт не синхронизируется и потеряется при смене телефона.

Системное приложение «Контакты» решает всё это годами и поддерживается
производителем устройства. Дублировать — значит наверняка сделать хуже.

## Три уровня

### Уровень 1 — делаем сами, безопасно
Критерий: операция не затрагивает агрегацию, набор полей и синхронизацию.

| Операция | Где | Почему безопасно |
|---|---|---|
| Избранное | `ContactQuickActions.setStarred` | Колонка агрегата, не участвует в синхронизации полей |
| Мелодия звонка | `setCustomRingtone` | Колонка агрегата. Для диалера — профильная функция |
| На голосовую почту | `setSendToVoicemail` | Колонка агрегата |
| Наши заметки и метки | Room | Вообще не в системных контактах |

Отправлять пользователя в другое приложение ради одной звёздочки —
издевательство, поэтому эти операции обязаны быть внутри.

### Уровень 2 — делаем сами, но с предупреждением

| Операция | Риск |
|---|---|
| Удаление контакта | Удаляется агрегат целиком, вместе с raw из **всех** аккаунтов. Отменить нельзя |

Только после явного подтверждения с объяснением последствий.

### Уровень 3 — отдаём системе

| Операция | Intent |
|---|---|
| Создать контакт | `ACTION_INSERT_OR_EDIT` |
| Добавить номер к существующему | `ACTION_INSERT_OR_EDIT` |
| Редактировать все поля | `ACTION_EDIT` |
| Сменить фото | `ACTION_EDIT` |
| Слияние дублей | Системное приложение |
| Группы | Системное приложение |
| Выбрать контакт или номер | `ACTION_PICK` |

**Отдельно про `ACTION_INSERT_OR_EDIT`.** Он не просто открывает форму:
если номер уже есть у кого-то из контактов, системное приложение само
предложит дополнить существующую запись вместо создания дубля. Это ровно
та логика, которую пришлось бы писать самим и которую легко сделать
неправильно.

## Что это даёт пользователю

- Правки применяются там же, где он привык, и выглядят как обычно
- Не появляются дубли и потерянные при синхронизации поля
- Контакт попадает в правильный аккаунт
- Работает с любым набором аккаунтов, включая корпоративный Exchange

## Что теряется

Переход в другое приложение — заметное переключение контекста. Смягчается:
- `finishActivityOnSaveCompleted` возвращает пользователя обратно
  сразу после сохранения;
- всё частое (избранное, мелодия, заметки, метки) остаётся внутри,
  и в системное приложение приходится уходить редко.

## Если однажды понадобится свой редактор

Разумная последовательность, а не всё сразу:

1. Быстрое создание: имя + номер, с **явным выбором аккаунта** в UI
2. Только создание нового raw-контакта, никогда не правка существующего
   агрегата
3. Проверка `RAW_CONTACT_IS_READ_ONLY` перед любой попыткой записи
4. Фото — последним: два варианта хранения и ограничения по размеру

Пункты 2 и 3 обязательны с самого начала: именно их нарушение
порождает неисправимые дубли.
