# Многопоточность и фоновая работа

## Правила проекта

**Ни одной блокирующей операции в главном потоке.** Проверяется StrictMode
в debug-сборке: нарушение даёт вспышку экрана и запись в лог.

**Диспетчеры внедряются, а не пишутся в коде.** `@IoDispatcher`
в конструкторе сразу показывает, что класс делает блокирующие операции,
и позволяет подставить тестовый диспетчер.

| Диспетчер | Для чего | Почему |
|---|---|---|
| `IO` | ContentResolver, файлы, Room, DataStore | Операции ждут, а не считают — пул до 64 потоков |
| `Default` | libphonenumber, T9-индекс, группировка | Счётная работа — пул по числу ядер |
| `Main` | только UI | |

**Работа, переживающая экран, идёт в `@ApplicationScope`.** Сохранение
заметки не должно отменяться из-за того, что пользователь закрыл карточку.

**`async` только внутри `coroutineScope`.** Запуск в `viewModelScope`
из вложенной функции ломает отмену: родительская задача отменяется,
а дочерние продолжают работать.

## Горячий путь: входящий вызов

Система даёт `CallScreeningService` порядка 5 секунд. Не уложились —
вызов проходит без нашего решения.

```
onScreenCall
  └─ collect (бюджет 1500 мс, withTimeout)
       ├─ async: PhoneLookup по номеру      ← точечный запрос по индексу
       ├─ async: правила из Room
       ├─ async: системный блок-лист
       ├─ async: метки номера
       └─ async: настройки (тоже параллельно)
  └─ SpamPolicy.evaluate — чистая функция, микросекунды
  └─ respondToCall
```

Было исправлено: раньше здесь вызывался `contacts.loadAll()`, читавший
всю телефонную книгу. На 2000 контактов это сотни миллисекунд, а под
нагрузкой — секунды, то есть риск не уложиться в бюджет и пропустить спам.

**При любой ошибке или таймауте вызов пропускается.** Молчащий телефон
вредит сильнее одного принятого спам-звонка.

## Дебаунс

`ContentObserver` на `CallLog` срабатывает несколько раз за один звонок:
система создаёт запись, дописывает длительность, затем кэшированное имя
и фото. Без задержки это четыре-пять полных перечитываний журнала подряд.

- Изменения провайдеров — **400 мс**
- Поиск по мере ввода — **120 мс**

Значения зафиксированы тестом: случайное изменение сделает интерфейс
вялым либо вернёт лишние перечитывания.

## Кэширование

`SubscriptionManager` и `TelecomManager` — binder-вызовы в системный
процесс. Список SIM нужен при отрисовке каждой строки журнала, поэтому
кэшируется; одновременные обращения синхронизируются `Mutex`, чтобы
запрос ушёл один раз, а не столько, сколько было вызывающих.

Сброс кэша — при изменении пользовательских имён слотов.

## Фоновая работа

| Задача | Механизм | Почему так |
|---|---|---|
| Активный вызов | Foreground-сервис, тип `phoneCall` | Обязателен с Android 14, процесс не должен умереть во время разговора |
| Постобработка завершённого вызова | WorkManager | `InCallService` живёт до конца вызова, система вправе убить процесс сразу после |
| Пересборка T9-индекса | WorkManager, одноразово + раз в 12 ч | Переживает перезапуск, не требует уведомления |
| Напоминание перезвонить | AlarmManager | Привязано к конкретному времени |

Foreground-сервис используется **только** для активного вызова.
Применять его для короткой фоновой задачи — злоупотребление,
которое Google Play отслеживает.
