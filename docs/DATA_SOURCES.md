# Откуда берутся данные

## Коротко

| Данные | Источник | Пишем ли мы |
|---|---|---|
| Журнал вызовов | `CallLog.Calls` (система) | Только удаление по команде пользователя |
| Контакты | `ContactsContract` (система) | Избранное, мелодия, голосовая почта; остальное — системному приложению |
| Заметки и метки | Наша база Room | Да |
| Чёрный и белый списки | Наша база Room | Да |
| Системный список блокировки | `BlockedNumberContract` | Да, как диалер по умолчанию |
| Предпочтения SIM | Наша база Room | Да |
| Настройки | DataStore | Да |

## Почему свой журнал вызовов не ведём

Записи в `CallLog.Calls` создаёт телефония Android — независимо от того,
какой диалер выбран по умолчанию. Дублировать это своей базой было бы
ошибкой по трём причинам.

**1. История переживает смену диалера.** Пользователь может вернуться
на штатный «Телефон» и не потерять ничего. Свой журнал сделал бы переход
к нам билетом в один конец — а это заметно отпугивает при установке.

**2. Один источник правды.** Мессенджеры, антивирусы и системные виджеты
читают тот же журнал. Два расходящихся списка порождают вопрос
«почему в Ogneliss звонок есть, а в системе нет» — и правы будут оба.

**3. Система уже делает работу за нас.** Заблокированные вызовы
помечаются `BLOCK_REASON`, имя и фото контакта кэшируются в записи,
принадлежность к SIM пишется в `PHONE_ACCOUNT_ID`.

`WRITE_CALL_LOG` нужен исключительно для удаления записей, когда
пользователь об этом просит.

### Что мы всё-таки храним у себя
Только то, чему в системном журнале места нет:

- заметки и метки к номерам (ключ — E.164, переживает удаление контакта);
- правила блокировки с масками;
- запомненный выбор SIM по номерам;
- T9-индекс — **кэш**, пересобирается из контактов и не является
  источником правды.

## Как отслеживаются изменения

Данные меняются **вне нашего приложения**: пользователь редактирует контакт
в системном приложении, синхронизация Google подтягивает записи, звонок
приходит при выключенном экране. Узнать об этом можно только от провайдеров.

```
CallLog.Calls ──── ContentObserver ──┐
                                      ├─ раздельные потоки
ContactsContract ─ ContentObserver ──┘
```

### Почему потоки раздельные

Операции разной стоимости:

| Событие | Что делаем | Стоимость |
|---|---|---|
| Изменился журнал | Перечитать страницу журнала | Дёшево |
| Изменились контакты | Перечитать книгу **и** пересобрать T9-индекс | Дорого |

Синхронизация аккаунтов трогает контакты пачками по несколько раз в час.
Перечитывать при этом журнал незачем. И наоборот: пересобирать индекс
из тысяч контактов после каждого звонка — расточительно.

### Три уровня отсечения лишней работы

**1. `selfChange`.** Провайдер сообщает, что изменение внесли мы сами
(например, удалили запись). Реагировать на собственное действие не нужно —
список уже обновлён напрямую.

**2. Дебаунс 400 мс.** Система пишет запись о звонке не один раз:
создаёт её, потом дописывает длительность, затем кэшированное имя и фото.
Без задержки это четыре-пять полных перечитываний подряд.

**3. Отметка времени правки книги.** `ContentObserver` срабатывает и на
служебные операции синхронизации, которые ничего не меняют по существу.
Перед перезагрузкой сравниваем `CONTACT_LAST_UPDATED_TIMESTAMP`
с сохранённым значением; совпало — пропускаем.

### Важная деталь подписки

```kotlin
cr.registerContentObserver(ContactsContract.Contacts.CONTENT_URI, true, observer)
                                                                  ↑
                                                    notifyForDescendants
```

Флаг обязателен. Правки приходят на дочерние URI конкретных контактов,
а не на корневой — без него изменение имени контакта осталось бы
незамеченным, и в журнале продолжало бы висеть старое.

### Отдельный поток уведомлений

`ContentObserver` вызывается на потоке своего `Handler`. С Looper главного
потока уведомления от синхронизации аккаунтов будили бы UI десятки раз
подряд. Свой `HandlerThread` снимает эту нагрузку.

## Что происходит при отзыве разрешений

Пользователь может отобрать доступ в любой момент. Тогда:

- журнал и контакты становятся недоступны — показывается пустое состояние
  с объяснением причины и кнопкой выдачи;
- наши собственные данные (заметки, правила) остаются: они в приватной базе
  и от разрешений не зависят;
- приложение продолжает работать с ограниченной функциональностью,
  а не падает.
