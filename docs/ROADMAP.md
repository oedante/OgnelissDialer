## Изменения относительно v59.0 — стабильность типов

### 🔴 Найдено главное: ни одна модель не была помечена @Immutable

Compose считает класс нестабильным, если у него есть поле типа `List`,
`Map`, `Set` или лямбда. **Нестабильные объекты считаются изменившимися
всегда** — Compose их не сравнивает.

Цепочка получалась такая: `CallLogGroup` содержит `List<String>` →
нестабилен → `CallLogRowState` содержит его → нестабилен → **каждая
строка списка перерисовывалась при любом обновлении данных**.

То есть вся предыдущая работа по подготовке строк заранее, кэшированию
форматирования и выносу вычислений в фон **пропадала впустую**: строки
всё равно перерисовывались все и всегда.

- [x] Помечены `CallLogGroup`, `Contact`, `PhoneNumber`, `SimSlot`,
      `CallLogEntry`, `NumberRule`, `NumberNote`, `NumberInfo`
- [x] Состояния экранов: `UiState`, `SettingsState`
- [x] Модели интерфейса: `CallLogFilter`, `CallStats`, `WizardStep`,
      `SimCallPlan.PerSim`

### `RevealAction` — отдельный случай

Класс содержит лямбду `onClick`, а функциональные типы нестабильны:
за лямбдой может стоять захват изменяемого состояния.

Список этих действий передаётся в **каждую** строку журнала —
нестабильность одного элемента делала весь список изменившимся
на каждом кадре.

### Контакты: та же ошибка, что чинили в журнале

`revealActionsFor` вызывался прямо в композиции для каждой строки:
создание списка объектов и чтение строк из ресурсов повторялось
на каждый кадр прокрутки.

- [x] Обёрнуто в `remember` по ключу контакта
- [x] Сама лямбда-фабрика тоже в `remember`: без него она пересоздавалась
      при каждой перерисовке, и Compose считал изменившимися все строки

### Проверка в prebuild_check
- [x] Модель с коллекцией или лямбдой без `@Immutable` теперь ломает
      проверку. Это ошибка, которую невозможно заметить глазами:
      компилятор молчит, а интерфейс просто «немного подтормаживает»

### Отчёт о стабильности
- [x] `./gradlew assembleRelease -Pcompose.metrics=true` выписывает,
      какие классы компилятор считает нестабильными и какие функции
      не пропускаемы

## Изменения относительно v58.0 — управление закреплёнными

### Зачем отдельный экран, если есть пункт в шторке

Шторка на карточке решает задачу «закрепить вот этого» — она под рукой
в момент, когда мысль возникла. Но три вещи через неё сделать нельзя:

- **посмотреть весь список** — закреплённых пять, держать их в голове
  не обязан никто;
- **поменять порядок** — он задаётся временем закрепления, и переставить
  через шторку можно только открепив и закрепив заново, потеряв позицию
  остальных;
- **открепить номер, которого нет на экране** — если человек не звонил
  давно, его карточка ушла за пределы загруженной страницы, и добраться
  до шторки нечем.

### Стрелки вместо перетаскивания

Перетаскивание в списке на телефоне ненадёжно: длинное нажатие
конфликтует с прокруткой, палец перекрывает перемещаемый элемент,
а промах возвращает всё на место без объяснения.

Две стрелки решают ту же задачу однозначно. Элементов не больше пяти —
перенести последний на первое место занимает четыре нажатия, и результат
каждого виден. Это зафиксировано отдельным тестом.

- [x] Номер позиции слева: показывает, где карточка окажется в журнале,
      и делает результат перестановки предсказуемым до нажатия
- [x] Стрелки у крайних элементов неактивны, но проверка есть
      и в логике — состояние интерфейса может отстать от данных

### Добавление через тот же экран контактов

- [x] Режим выбора вместо отдельного списка. Заводить второй означало бы
      поддерживать два поиска, две группировки и два набора свайпов —
      и они разошлись бы при первой же правке
- [x] Отличий три: заголовок объясняет задачу, нажатие возвращает
      выбранное вместо открытия карточки, свайпы не мешают
- [x] Кнопка добавления **неактивна при достижении предела**: активная
      кнопка, ведущая к отказу, сбивает с толку

### Пустое состояние подсказывает второй способ
- [x] «Закрепить номер можно и удержанием записи в журнале» — иначе
      человек, попавший сюда из настроек, не узнает про быстрый путь

## Изменения относительно v57.0 — закреплённые и экспорт истории

### Закреплённые абоненты

**Чем отличается от избранного.** Избранное — свойство КОНТАКТА:
хранится в телефонной книге, синхронизируется с Google, видно всем
приложениям. Закрепление — свойство ЖУРНАЛА у нас: «держи этот номер
наверху, пока я с ним разбираюсь».

Курьер, мастер, разовый клиент — их не заносят в избранное, потому что
через неделю они там будут мешать. Закрепить же можно и номер, которого
в книге нет вовсе, — для избранного это невозможно в принципе.

- [x] До пяти номеров. Больше — журнал начинался бы ниже видимой
      области, и приложение открывалось бы «пустым»
- [x] **Порядок — тот, в котором закрепляли**, а не по дате звонка.
      Иначе карточки прыгали бы местами при каждом входящем,
      и мышечная память «мастер второй сверху» переставала бы
      работать — а ради неё закрепление и делается
- [x] Новый номер добавляется в конец: закреплённые раньше остаются
      на местах
- [x] При достижении предела показывается причина, а не молчаливый отказ
- [x] **При поиске закрепление не применяется:** человек ищет конкретного
      абонента, поднимать наверх посторонних было бы помехой
- [x] Свой префикс ключа свайпа: запись остаётся и в общем списке,
      и без префикса открытие панели у закреплённой карточки открывало
      бы её и внизу
- [x] 12 тестов

**Попутный рефакторинг.** Строка журнала выводится теперь в двух местах,
и её описание вынесено в отдельный компонент. Держать восемьдесят строк
в теле `items` дважды означало бы, что при следующей правке одну копию
забудут, а различие проявится как «у закреплённых свайп работает иначе».

### Экспорт истории по абоненту

Три реальных случая, и все три про то, что журнал нужен **за пределами
телефона**: спор с оператором, отчёт по времени переговоров с клиентом,
заявление о телефонном мошенничестве.

- [x] Текстовая сводка: статистика, заметка с метками, список вызовов
- [x] **Обычный текст, а не CSV.** CSV удобен машине, но человеку его
      нужно открыть в таблице, где он рассыплется из-за разделителей
      и кодировки. Текст читается везде и вставляется в письмо как есть
- [x] Отдельный `asCsv` для тех, кому нужна таблица, — с точкой
      с запятой: в русской локали Excel ждёт именно её, файл с запятыми
      открывается одной строкой
- [x] **Оговорка об отсутствии записи разговоров.** Без неё документ
      выглядит как полный отчёт, и отсутствие содержания читается
      как пропуск, а не как факт
- [x] Отправка через системный лист, а не сохранение в файл: выгрузку
      почти всегда нужно кому-то отправить, и «сохранить, найти,

## Изменения относительно v55.0 — тяжёлые операции в фон

### 🔴 Обработка прочитанного шла в главном потоке

Чтение из провайдеров давно вынесено в `IO`. Но **обработка
прочитанного** оставалась на главном потоке, потому что `viewModelScope`
использует `Dispatchers.Main.immediate`.

Корутина не означает фоновый поток: она означает возможность
приостановиться. Без явного `withContext` работа идёт там, где запущена.

| Операция | Что делает | Где было заметно |
|---|---|---|
| Группировка журнала | Перебор и склейка 3000 записей | Подгрузка при прокрутке |
| Разбивка по датам | Календарная группа для каждой записи | То же |
| Определитель номера | Разбор через libphonenumber | Открытие приложения |
| Статистика | Обход журнала с суммированием | Каждое обновление |
| Ярлыки | Сортировка журнала, обход контактов | Каждое обновление |
| Фильтр контактов | Фильтрация, поиск, разбивка по буквам | Каждое нажатие в поиске |

Всё переведено на `Default` — счётный пул по числу ядер.

### Почему Default, а не IO

Частая ошибка — пускать счётную работу на `IO`. Она не сломается,
но пул `IO` растёт под ожидание: он рассчитан на заблокированные потоки,
которые ничего не делают. Для счёта больше потоков, чем ядер,
не ускоряет ничего, а переключения контекста съедают выигрыш.

### Контакты: один переход вместо трёх

Фильтр, поиск по имени и разбивка по буквам идут подряд и зависят
друг от друга. Три отдельных `produceState` дали бы три переключения
потока и три промежуточных состояния списка на экране.

`produceState` показывает прежний результат, пока считается новый:
список не мигает пустотой при вводе каждой буквы.

### `remember` — не фоновый поток

Отдельно стоит отметить, потому что выглядит обманчиво: `remember`
запоминает результат между перерисовками, но **вычисляет его в потоке
композиции**, то есть в главном. Для дорогих вычислений нужен
`produceState` с явным `withContext`.

### Чего НЕ выносили

- Отметку избранного, переключение SIM, установку фильтра: запись
  одного значения, переключение потока дороже самой операции
- Показ результата: обновление состояния Compose должно идти
  на главном потоке
- Фильтрацию избранных контактов: их единицы, проверка флага стоит
  наносекунды

### Новый документ
- [x] `docs/THREADING.md` — где что выполняется, три диспетчера
      и когда какой, ловушка с `viewModelScope`

### 🔴 Диалог выбора не перерисовывался (пункты 3, 6)


Обычный вызов функции, а не чтение состояния. Compose не видел

Поле `STARRED` запрашивалось у таблицы `Phone`, где оно **присоединяется**

`contactId` разбирался из `CACHED_LOOKUP_URI`, но на многих прошивках

Подписка на провайдер устанавливается в `init` ViewModel, и если
разрешение выдали позже — второй попытки не происходило. Плюс во время
разговора приложение в фоне, и часть прошивок придерживает уведомления.

Добавлено обновление при возвращении на передний план. Для диалера

## Изменения относительно v52.0 — настройка чувствительности свайпа

### Зачем это в настройках

Подобрать пороги «на глаз» невозможно: они зависят от размера телефона,
от того, держат его одной рукой или двумя, от скорости движений
конкретного человека. То, что для одного «срабатывает слишком легко»,
для другого «приходится тянуть через весь экран».

### Четыре параметра, а не один «уровень чувствительности»

Одна шкала «слабее — сильнее» выглядела бы проще, но за ней стоят три
независимые величины, и людям мешают разные из них.

| Параметр | Кому нужен |
|---|---|
| Расстояние свайпа | Тем, кому приходится тянуть слишком далеко |
| Порог защёлкивания | Тем, у кого жест ощущается неуправляемым |
| Скорость броска | Тем, у кого срабатывает при обычной прокрутке |
| Горизонтальное начало | Тем, у кого палец при листании идёт по дуге |

Свести это в один ползунок значило бы лишить половину пользователей
возможности починить именно свою проблему.

### Пробная строка на том же экране

Главное решение здесь. «140 dp» ничего не говорит о том, как жест
ощущается пальцем. Без возможности попробовать на месте настройка
превращается в угадывание, а проверка требовала бы выхода на главный
экран и обратно по три раза на каждое значение.

- [x] Вверху экрана **настоящий компонент свайпа** с текущими значениями
      ползунков, а не имитация: имитация вела бы себя иначе, и подобранные
      на ней значения не совпали бы с поведением в журнале
- [x] Подпись, что именно сработало — иначе непонятно, засчитался жест
      или нет
- [x] Значение показано числом рядом с ползунком: по его положению
      вернуться к прежней настройке невозможно

### Сброс к значениям по умолчанию

- [x] Кнопка в панели, появляется **только когда есть что сбрасывать**
- [x] Сброс **удаляет ключи**, а не записывает текущие значения
      по умолчанию. Разница важна: если в следующей версии значения
      изменятся, пользователь получит новые, а не замороженные старые

Пороги были константами внутри `SwipeRevealRow`, и при изменении

не применились — свайп остался чутким, хотя в дорожной карте значилось
иначе.

- [x] Теперь источник один: `SwipeTuning`. Рассинхронизация невозможна
- [x] 6 тестов фиксируют значения по умолчанию и границы ползунков

- [x] Нижние не позволяют вернуть ту самую проблему: меньше 60 dp —

Проверка велась не по памяти, а поиском по коду. Выяснилось, что

| Параметр | Заявлено в v43 | Было на самом деле | Стало |
|---|---|---|---|
| Порог защёлкивания | 0.75 | **0.4** | 0.75 |

Это объясняет, почему свайп оставался слишком чутким, а строка

**Вывод для дальнейшей работы:** заявленное исправление нужно проверять
поиском по коду, а не считать выполненным по факту правки.

### 🔴 Причина падения найдена: неуникальные ключи

`LazyColumn` требует уникальных ключей и падает с «Key was already used»,
как только два элемента совпадут.

Ключом служил идентификатор абонента. В режиме «подряд идущие» один
человек даёт **несколько карточек**: позвонил утром, потом кто-то другой,
потом он же вечером — ключи одинаковые.

То есть падение происходило у любого пользователя с повторными звонками,
то есть у всех.

- [x] Ключ карточки дополнен идентификатором последнего вызова
- [x] **3 теста** проверяют уникальность во всех трёх режимах группировки

### 🔴 Кэш определителя не работал

```kotlin
.filterNot { it in cache }   // cache — ConcurrentHashMap
```

Оператор `in` у `ConcurrentHashMap` вызывает унаследованный `contains()`,
который проверяет **значения**, а не ключи. Проверка молча возвращала
false, и запросы уходили повторно для уже известных номеров.

- [x] Заменено на `containsKey`

## Изменения относительно v41.0 — диагностика падения

Приложение падает сразу после выдачи разрешений, стека в logcat нет.

### 🔴 Найдена ошибка в этом самом пути

`SimRepository.startWatching` использовал `context.mainExecutor`.
Метод появился в **API 28**, а minSdk у нас **26**: на Android 8.0 и 8.1
обращение к нему даёт `NoSuchMethodError`.

Вызывается он при подписке на смену SIM, то есть ровно тогда, когда
выдано разрешение на телефон. Совпадение с описанным симптомом полное.

- [x] Executor собирается вручную через `Handler(Looper.getMainLooper())`

На Android 15 эта ошибка не проявится — но найдена она была именно
при разборе, и на старых устройствах привела бы к тому же симптому.

### Путь после выдачи разрешений закрыт защитой

Это момент, когда приложение впервые получает доступ к журналу
и контактам, и впервые выполняется код, до этого молча возвращавший
пустые списки.

- [x] Подписка на провайдеры, обновление данных, ярлыки и подписка
      на смену SIM — каждый шаг обёрнут отдельно
- [x] Сбой одного не уносит приложение: пользователь только что дал
      доступ и ждёт, что всё заработает

### Отметка этапа работы

Бывают падения, после которых в logcat пусто: процесс убит системой,
буфер переполнен чужим приложением, сбой произошёл в потоке, чей стек
не попал в отчёт.

В такой ситуации помогает знать, **что приложение делало последним**.

- [x] `Stage` — одна строка, обновляемая на ключевых переходах
- [x] Перехватчик падений сохраняет её в `SharedPreferences` через

      процесса, и асинхронная запись может не успеть
- [x] При следующем запуске первая строка лога сообщает, на чём
      оборвалось в прошлый раз
- [x] Стек пишется сразу в три места: `android.util.Log`, файл лога

## Изменения относительно v39.0 — тесты интерфейса

### Зачем тестовые заглушки, если код уже написан

Вопрос возник по ходу работы, и ответ стоит записать.

Заглушки **не заменяют нереализованный код**. Настоящие реализации
написаны и работают: `CallLogRepository` читает системный журнал,
`RulesRepository` пишет в Room, `ContactQuickActions` меняет контакты.
Всё это лежит в `app/src/main/` и попадает в приложение.

Заглушки лежат в `app/src/test/` — этот каталог **в APK не входит**,
пользователь его не получает.

Они заменяют не реализацию, а **телефон**. Чтобы проверить, что подгрузка
запрашивает верное смещение, настоящему репозиторию нужен реальный журнал
вызовов на устройстве. Тест с заглушкой выполняется за миллисекунды
на любой машине и в CI, где устройства нет вовсе.

### Что уже работало верно

### Чего не хватало: возможность взять роль себе

### 🔴 Третий вариант ответа на вызов

Держателю роли определителя доступен `CallResponse.setSilenceCall` —
**беззвучный пропуск**: телефон не звонит, но вызов проходит и остаётся
в журнале.

| Ответ | Звонит | В журнале | Кому доступен |
|---|---|---|---|
| Пропустить | Да | Да | Всем |
| **Беззвучно** | **Нет** | **Да** | **Держателю роли** |
| Отклонить | Нет | Как заблокированный | Всем |

**Разница принципиальна.** Блокировка необратима: если эвристика
ошиблась, человек не узнает, что ему звонили. Беззвучный пропуск ошибку
прощает — звонок виден, можно перезвонить.

Раньше оценка риска давала только «пропустить или заблокировать»,
и на пограничных значениях приходилось выбирать между двумя плохими
вариантами. Теперь решение разделено по степени уверенности:

- **95 и выше** — блокировка
- **порог … 95** — беззвучный пропуск
- **ниже порога** — обычный вызов

- [x] `SpamPolicy.Action` с тремя значениями вместо булева `block`
- [x] Явные правила пользователя блокируют, а не заглушают: он сам
      добавил номер в чёрный список, сомнений нет, и смягчать его решение
      неправильно
- [x] Платные номера блокируются независимо от уверенности — единственная
      категория, где ошибка стоит денег
- [x] **Без роли определителя SILENCE трактуется как ALLOW**: лучше
      сомнительный звонок со звуком, чем блокировка по догадке
- [x] 5 тестов на разделение уровней

## Изменения относительно v30.0 — единый стиль и устойчивый запуск

### 🔴 Вероятная причина падения при повторном открытии

«Падает при запуске, помогает только очистка данных» — характерный
признак несовпадения схемы Room.

Room сверяет контрольную сумму схемы с сохранённой в базе. При расхождении
бросает `IllegalStateException` — «Room cannot verify the data integrity».
Происходит это при **первом же обращении к базе**, то есть сразу после
запуска. Очистка данных удаляет файл, и он создаётся заново по актуальной
схеме — отсюда и «помогает только очистка».

Расхождение возникает в разработке постоянно: сущность изменена,
версию базы поднять забыли.

- [x] **Разрушительная миграция включена только в debug.** В release
      её нет и быть не должно: там расхождение схемы означает ошибку
      в миграции, и молча стирать заметки, метки и списки блокировки
      пользователя недопустимо. Пусть лучше упадёт на нашем тестировании,
      чем потеряет данные у людей
- [x] Каждый шаг инициализации в `Application` обёрнут отдельно: сбой
      создания каналов уведомлений или постановки фоновой индексации
      больше не мешает запуску. Звонить приложение сможет и без них

### 🔴 `KSP failed: The name 'default' cannot be used because it is a Java keyword`

В `DispatchersModule` была функция `@Provides fun default()`.

Hilt превращает имя `@Provides`-функции в имя генерируемого **Java**-метода.
`default` — ключевое слово Java с версии 8. Генерация падала.

Коварство в том, что **из Kotlin-кода причина не видна**: компилятор Kotlin
не возражает, `default` для него обычный идентификатор. Ошибка приходит
на этапе генерации, и сообщение не называет файл.

- [x] Все `@Provides`-функции переименованы с префиксом `provide`.
      Это не стиль, а защита: заодно закрывает `native`, `final`,
      `static`, `record` и прочие слова, ключевые в Java, но не в Kotlin
- [x] **Проверка добавлена в `prebuild_check.py`** — теперь ловится
      за секунды до сборки

### Исправления в модуле замеров
- [x] `kotlinOptions` → `compilerOptions` (в Kotlin 2.x первый даёт ошибку)
- [x] `managedDevices.set(...)` → `managedDevices += ...`: это изменяемая
      коллекция, а не `Property`
- [x] `useConnectedDevices.set(...)` → `useConnectedDevices = ...`
- [x] Устройство замеров приведено к существующему образу
- [x] `warnings { maxAgpVersion = false }` — плагин ругается на версии AGP

## Изменения относительно v20.0 — мелодия звонка отдана системе

### Оценка громкости по микрофону — отклонено

Идея замерять уровень шума перед звонком отвергнута по четырём причинам:

1. **`RECORD_AUDIO` в диалере — худшее из возможных разрешений.**
   Пользователь решит, что приложение пишет разговоры. Шесть итераций
   доверия строились на «нет доступа в интернет» — одна строчка в манифесте
   разрушила бы это.
2. **С Android 14 микрофон даёт зелёный индикатор в статус-баре.**
   Каждый входящий начинался бы с мигания «микрофон используется».
3. **Из фона микрофон недоступен** без foreground-сервиса типа `microphone`.
   У нас тип `phoneCall`; второй означал бы новую декларацию в Play.
4. **Задержка.** Инициализация `AudioRecord` плюс окно замера —
   200–500 мс перед началом звонка.

### 🔴 Найдено попутно: беззвучные входящие вызовы

При проработке обнаружилось, что в манифесте стоял флаг
`IN_CALL_SERVICE_RINGING = true`, а проигрывателя мелодии не было.

Флаг означает, что приложение берёт воспроизведение на себя, и система
свой рингтон **подавляет**. То есть входящие вызовы приходили бы
беззвучно — при внешне исправном приложении.

Обнаружить это на эмуляторе невозможно: там входящих вызовов не бывает.
Ошибка вылезла бы у первого же тестировщика на реальном устройстве,
но объяснить её причину было бы непросто.

### Решение: мелодию проигрывает система ✅

Флаг убран. Что мы получаем бесплатно и что пришлось бы воспроизводить
самим на каждой прошивке:

- персональная мелодия контакта;
- «Не беспокоить» со всеми исключениями и правилами;
- вибро и беззвучный режимы;
- рабочий профиль;
- вспышка и другие настройки доступности;
- у Samsung, Xiaomi и ряда других — **собственное нарастание громкости**
  в системных настройках звука, которое мы бы просто продублировали.

- [x] `IN_CALL_SERVICE_RINGING` убран, в манифесте оставлено развёрнутое
      объяснение почему — чтобы флаг не вернули «для порядка»
- [x] `RingtoneController` и `AdaptiveRingtonePolicy` удалены: мёртвый код
      хуже отсутствующего
- [x] **`scripts/check_ringing_flag.sh` в CI** — валит сборку, если флаг
      появится без проигрывателя. Класс ошибки, который иначе доходит
      до пользователя молча

### Персональная мелодия контакта ✅

Раз мелодию играет система, назначать её мы всё равно можем — и это
работает лучше собственного проигрывателя.

- [x] Выбор через системный диалог `ACTION_RINGTONE_PICKER`: показывает
      встроенные звуки, файлы производителя и пользователя. Свой список
      потребовал бы чтения MediaStore и разрешения на доступ к аудиофайлам
- [x] Пункты «По умолчанию» и «Без звука»: беззвучный контакт —
      рабочий сценарий
- [x] Записывается в `CUSTOM_RINGTONE` системного контакта, поэтому
      **работает и в штатном «Телефоне»**. Пользователь не привязан
      к нам своей настройкой — это принципиально, как и с журналом вызовов

### Что осталось от идеи адаптивной громкости

Ничего, и это правильный итог. Задачу «тихо в комнате, громко на улице»
решает нарастающая громкость, которая у большинства производителей
уже есть в системных настройках. Дублировать её в приложении —
добавлять вторую настройку с тем же смыслом и получать вопросы
«почему их две и какая главнее».

В настройках оставлена ссылка на системные параметры звука.

      разные. С одним порогом звук «дребезжал» бы между динамиками
      несколько раз в секунду при дрожании руки — хуже, чем отсутствие
      функции вовсе
- [x] **Задержка 800 мс.** Человек кладёт телефон примерно за полсекунды,
      случайное движение длится меньше
- [x] **Уступка ручному выбору.** Если пользователь сам нажал кнопку
      динамика, датчики молчат до конца разговора. Иначе приложение
      спорит с ним: он включил громкую связь, поднёс телефон к уху
      что-то сказать — и связь выключилась против его воли
- [x] **Гарнитура отменяет автоматику** и заодно отписывает от датчиков:
      разговор может длиться час, лишний расход батареи ни к чему
- [x] `SENSOR_DELAY_UI`, а не `FASTEST` — смена положения телефона
      это событие в масштабе секунд
- [x] Порог близости берётся из `maximumRange` самого датчика:
      у одних он 5 см, у других 1 см
- [x] **Выключено по умолчанию.** Внезапно заоравший динамик
      на совещании пугает сильнее, чем радует удобство
- [x] 14 тестов `SmartSpeakerPolicy`

### 2. «Перезвони мне позже» ⚠️ замысел изменён

Идея «всплывающая кнопка на 3 секунды» упирается в две проблемы:

**Окно поверх других приложений требует `SYSTEM_ALERT_WINDOW`**, которое
выдаётся не диалогом, а походом в настройки. Большинство пользователей
его не даёт, и функция для них просто не существует.

**Три секунды — слишком мало.** Вызов сбрасывают на бегу, за рулём,
на совещании. Ровно в этих ситуациях в экран не смотрят, и кнопка
исчезнет незамеченной. А функция задумана именно для «сбросил и забыл».

**Сделано уведомлением с кнопками.** Живёт в шторке, пока не смахнут,
работает без особых разрешений, доступно из любого приложения.
Варианты выбора прямо в нём: через 30 минут, через 2 часа, вечером.

- [x] «Вечером» = 19:00, а если уже позже — завтра. Напоминание
      в прошедшее время сработало бы немедленно
- [x] **Календарь остаётся опцией.** Прямая запись требует
      `WRITE_CALENDAR` — ещё одно чувствительное разрешение ради того,
      что прекрасно работает на AlarmManager. Вместо этого `ACTION_INSERT`
      открывает календарь с заполненными полями, разрешений не требует,
      создание подтверждает сам пользователь

### 3. Аудит забытых контактов ⚠️ реализовано с жёсткими ограничениями

Здесь обнаружился подвох, способный навредить.

**Проблема первая: отсутствие звонков ≠ отсутствие общения.** С человеком
можно ежедневно переписываться в мессенджере, обмениваться почтой,
видеться лично — и ни разу не позвонить. Предложение удалить такой контакт
это прямой вред.

**Проблема вторая, опаснее: системный журнал хранит ограниченную историю.**
Android держит порядка 500 записей, производители режут ещё сильнее.
Если журнал покрывает три месяца, вывод «не звонили два года» будет
ложным для **каждого** контакта в книге.

Защиты, зашитые в код:

- [x] **Проверка глубины журнала.** Если история не покрывает заявленный
      период — аудит не запускается вовсе и честно объясняет, почему
- [x] Функция называется «пересмотреть», а не «удалить». Никакого
      массового действия и кнопки «удалить всё»
- [x] Избранные, контакты с заметками и метками исключаются: пользователь
      уже показал, что они важны
- [x] Отсутствие звонков в журнале помечается **отдельно** от подтверждённой
      давности — это разные по надёжности выводы, и формулировки разные
- [x] Список ограничен 20 позициями: 200 имён никто не разберёт
- [x] Явная оговорка в интерфейсе: «отсутствие звонков не означает
      отсутствие общения»
- [x] Давность считается по последнему звонку **любого** номера контакта
- [x] **Выключено по умолчанию**
- [x] 11 тестов `ContactAuditor`

## Изменения относительно v18.0 — источники данных, отслеживание изменений, переходы

### Откуда берутся данные — зафиксировано документом

Вопрос возник по ходу работы, ответ стоит записать явно.

**Свой журнал вызовов не ведём.** Записи в `CallLog.Calls` создаёт телефония
Android независимо от выбранного диалера. Дублировать своей базой нельзя
по трём причинам:

1. **История переживает смену диалера.** Пользователь может вернуться
   на штатный «Телефон» и не потерять ничего. Свой журнал сделал бы
   переход к нам билетом в один конец — это заметно отпугивает
   при установке.
2. **Один источник правды.** Мессенджеры и антивирусы читают тот же журнал.
   Два расходящихся списка порождают вопрос «почему в Ogneliss звонок есть,
   а в системе нет», и правы будут оба.
3. **Система уже делает работу за нас:** помечает заблокированные вызовы
   через `BLOCK_REASON`, кэширует имя и фото, пишет принадлежность к SIM.

`WRITE_CALL_LOG` нужен только для удаления записей по команде пользователя.
В своей базе — лишь то, чему в системе места нет: заметки, метки, правила,
предпочтения SIM и T9-индекс (это кэш, а не источник правды).

- [x] `docs/DATA_SOURCES.md` — таблица источников и правил записи

### 🔴 Найдено: один общий наблюдатель на разные по стоимости операции

Был единственный `ContentObserver` на журнал и контакты сразу, и любое
уведомление вызывало полную перезагрузку всего.

Проблема в том, что это операции несопоставимой стоимости:

| Событие | Работа | Стоимость |
|---|---|---|
| Изменился журнал | Перечитать страницу | Дёшево |
| Изменились контакты | Перечитать книгу **и** пересобрать T9-индекс | Дорого |

Синхронизация аккаунтов трогает контакты пачками по несколько раз в час —
и каждый раз перечитывался журнал. А после каждого звонка впустую
пересобирался индекс из тысяч контактов.

### Исправлено ✅ — три уровня отсечения лишней работы

- [x] **Раздельные потоки** для журнала и контактов
- [x] **`selfChange`**: провайдер сообщает, что правку внесли мы сами
      (например, удалили запись). Реагировать на собственное действие
      не нужно — список уже обновлён напрямую
- [x] **Дебаунс 400 мс** (был и раньше)
- [x] **Отметка времени правки книги.** Перед перезагрузкой сравниваем
      `CONTACT_LAST_UPDATED_TIMESTAMP` с сохранённым. Совпало — уведомление
      служебное, пропускаем. Это отсекает большую часть событий
      от синхронизации аккаунтов
- [x] **`notifyForDescendants = true`** при подписке на контакты. Флаг
      обязателен: правки приходят на дочерние URI конкретных контактов,
      а не на корневой. Без него изменение имени осталось бы незамеченным,
      и в журнале продолжало бы висеть старое
- [x] **Свой `HandlerThread`** для уведомлений. С Looper главного потока
      события синхронизации будили бы UI десятки раз подряд
- [x] Пересборка T9-индекса запускается **только** при реальном изменении
      контактов, а не по расписанию и не после звонков

использовать сеть. Скрывать это было бы нечестно на фоне остальных
обещаний приложения; само оно по-прежнему в сеть не ходит.

## Изменения относительно v14.0 — постраничная загрузка журнала

Снят жёсткий лимит в 500 записей. Журнал теперь подгружается по мере
прокрутки, потолок накопления — 3000 записей.

### ⚠️ Почему НЕ Paging 3

В плане с седьмой итерации стояло «Paging 3 для журнала». При реализации
выяснилось, что библиотека для этой задачи не подходит — по двум причинам,
обе архитектурные.

**1. Границы страниц ломают группировку.** В режиме «подряд идущие»
последняя карточка страницы N и первая карточка страницы N+1 могут
оказаться вызовами одного абонента. Их нужно склеить, а Paging обрабатывает
страницы независимо и не даёт доступа к соседним.

Результат наивной реализации — видимый артефакт: «Любимая (3)» и сразу
под ней «Любимая (2)» вместо «Любимая (5)». Причём поймать это вручную
почти невозможно: нужна подходящая история звонков ровно на границе
страницы, а граница зависит от размера экрана и скорости прокрутки.

**2. Режим «все вызовы абонента» требует полного просмотра.** Чтобы собрать
все звонки человека в одну карточку и отсортировать карточки по последнему
вызову, нужно прочитать журнал целиком. Постранично это невозможно
в принципе: очередная страница может содержать старый звонок абонента,
чья карточка уже показана выше — её пришлось бы двигать вверх задним числом.

**Принятое решение:** собственный `CallLogPager`. Страницы накапливаются
в памяти, группировка каждый раз пересчитывается по всему набору.
Дороже, чем Paging, но корректно: группировка 2000 записей на `Default`
занимает единицы миллисекунд, а память под 3000 записей — порядка мегабайта.

### Реализовано ✅

- [x] `loadEntries(limit, offset)` — постраничное чтение провайдера.
      LIMIT/OFFSET передаются в строке сортировки: отдельного параметра
      для этого в API ContentProvider нет
- [x] Размер страницы 150 записей — примерно пять экранов прокрутки
- [x] Подгрузка начинается **за пять элементов до конца**, а не по достижении
      дна: запрос успевает завершиться раньше, чем пользователь долистает
- [x] Защита от повторных вызовов: `LazyColumn` при быстрой прокрутке
      дёргает обработчик много раз подряд, без защиты запустилось бы
      несколько параллельных загрузок одной страницы
- [x] **Отсечение дублей по id.** Между запросами журнал мог измениться
      (пришёл новый звонок), смещение «съезжает», и провайдер вернёт уже
      загруженные записи. Без отсечения счётчики в карточках удвоились бы
- [x] Потолок накопления 3000 записей; у потолка запрашивается только
      остаток, а не полная страница
- [x] Индикатор подгрузки показывается только когда есть что грузить:
      вечный спиннер в конце короткого журнала читается как зависание
- [x] Определитель номера досчитывается для новых карточек, не блокируя
      показ списка

### Тесты
- [x] 12 тестов `CallLogPager`. Ключевой — склейка вызовов одного абонента
      на стыке страниц, ровно тот случай, ради которого пришлось отказаться

- [x] Проверка частичного пересечения страниц и отсечения дублей

Два опасных случая ловятся до сохранения, а не после:

**1. Правило, которое молча не работает.** Номера сравниваются в формате
E.164, поэтому введённое «8 (900) 123-45-67» не совпало бы ни с чем.
Правило лежало бы в списке, выглядело рабочим — и пропускало звонки.
Это худший вид бага: приложение кажется исправным.

Теперь ввод нормализуется, а под полем показывается, **что именно**

которое действительно совпадёт с бесплатными линиями.

**2. Слишком широкий шаблон.** «+7*» заблокировал бы все российские
номера. Отклоняется с объяснением: нужно минимум три значащие цифры.

- [x] `RulePattern` — чистая логика, 14 тестов
- [x] Ключевой тест проверяет не сохранение шаблона, а его **срабатывание**
      на реальных номерах: маска 8-800 обязана ловить бесплатные линии
      и не трогать мобильные

## Изменения относительно v12.0 — стратегия работы с контактами

### Решение: гибрид с перевесом в сторону системного приложения

Полный редактор контактов внутри Ogneliss **не реализуется**.

**Разрешения тут ни при чём.** `WRITE_CONTACTS` уже заявлено и, в отличие
от `CALL_LOG` и `PHONE`, отдельной декларации в Google Play не требует.
Формальных препятствий нет.

**Препятствие — модель данных ContactsContract.** Цена ошибки особенная:
портятся данные, которые живут вне нашего приложения и нужны десятку
других программ.

Четыре ловушки, из-за которых свой редактор почти наверняка сделает хуже:

1. **Агрегация.** Один «контакт» — склейка нескольких `RawContacts`:
   Google, локальный, SIM, плюс свои записи добавляют мессенджеры.
   Нужно выбирать, в какой raw писать; ошибка порождает дубли.
2. **Аккаунты ограничивают набор полей.** Неподдерживаемое поле теряется
   при первой синхронизации — молча. Пользователь заметит через неделю
   и не поймёт причину.
3. **Часть raw только для чтения** (записи мессенджеров).
4. **В какой аккаунт создавать новый контакт?** Ошибка означает, что
   контакт не синхронизируется и потеряется при смене телефона.

### Три уровня ✅

**Уровень 1 — делаем сами.** Критерий: операция не затрагивает агрегацию,
набор полей и синхронизацию.
- [x] Избранное — колонка агрегата
- [x] Персональная мелодия звонка — для диалера профильная функция
- [x] Переадресация на голосовую почту
- [x] Наши заметки и метки (вообще не в системных контактах)

Отправлять пользователя в другое приложение ради одной звёздочки —
издевательство, поэтому это обязано быть внутри.

**Уровень 2 — делаем сами, но с предупреждением.**
- [x] Удаление контакта. Удаляется агрегат целиком, вместе с записями
      из **всех** аккаунтов, включая Google. Диалог подтверждения
      объясняет именно это, а не спрашивает абстрактное «вы уверены?»

**Уровень 3 — отдаём системе.**
- [x] Создание, редактирование всех полей, смена фото, слияние дублей,
      группы, выбор контакта
- [x] `ACTION_INSERT_OR_EDIT` вместо `ACTION_INSERT`: если номер уже есть
      у кого-то, системное приложение само предложит дополнить запись
      вместо создания дубля. Это ровно та логика, которую пришлось бы
      писать самим и легко сделать неправильно
- [x] `finishActivityOnSaveCompleted` возвращает пользователя обратно
      сразу после сохранения — переключение контекста смягчается
- [x] Проверка `RAW_CONTACT_IS_READ_ONLY`: кнопка правки не показывается
      для контактов, которые редактировать нельзя

### Архитектурное разделение
- [x] `ContactsRepository` — только чтение
- [x] `ContactQuickActions` — безопасные изменения
- [x] `ContactEditor` — переадресация в системное приложение

Так проще следить за тем, кто и что пишет в системные контакты:
все точки записи собраны в двух файлах вместо размазывания по коду.

### Новый документ
- [x] `docs/CONTACTS_STRATEGY.md` — обоснование, таблица уровней и план
      на случай, если свой редактор всё же понадобится

### Если однажды понадобится свой редактор
Порядок, а не всё сразу:
1. Быстрое создание «имя + номер» с **явным выбором аккаунта** в UI
2. Только создание нового raw, никогда не правка существующего агрегата
3. Проверка `RAW_CONTACT_IS_READ_ONLY` перед любой записью

`SpamInputCollector` вызывал `contacts.loadAll()` — чтение **всей**

операция занимает сотни миллисекунд, а на слабом устройстве под нагрузкой

### Свайп-панель доведена до боевого состояния ✅

## Изменения относительно v9.0 — выбор номера и SIM

### Разделённая кнопка вызова ✅

При двух активных SIM кнопка внизу клавиатуры делится пополам:
слева вызов с SIM 1, справа с SIM 2, с номером карты на каждой половине.

Альтернатива — одна кнопка и диалог выбора после нажатия — добавляет лишний
шаг к самому частому действию приложения. Разделённая кнопка убирает его
целиком. Обе половины по 56 dp в высоту и не меньше 100 dp в ширину,
между ними разделитель: без него две половины читаются как одна кнопка
и пользователь не догадается о выборе.

При одной SIM кнопка обычная — номер карты не показывается.

### Выбор номера перед действием ✅

Шторка снизу со всеми номерами абонента. Для каждого: номер целиком,
подпись из книги, направление последнего вызова (↗ / ↙), бейдж SIM,
с которой звонили, и ряд действий — вызов с каждой SIM, SMS, мессенджер.

Шторка, а не диалог: она появляется у большого пальца, тогда как диалог
возникает по центру экрана, куда одной рукой не дотянуться.

### Свайп с несколькими номерами — принятый компромисс

Идея показывать в свайпе несколько иконок с последними цифрами упирается
в физику: при трёх и более целях шириной 56 dp под движущимся пальцем
промахи становятся правилом. Реализован гибрид:

| Номеров | Поведение свайпа |
|---|---|
| **Один** | Сразу выполняет действие. Быстро и привычно — это большинство случаев |
| **Два-три** | Открывает панель с кнопками, помеченными «…05-12». Панель фиксируется открытой, нажатие спокойное |
| **Больше трёх** | Открывает полную шторку, где номера видны целиком с подписями |

Ключевое отличие от обычного swipe-to-dismiss: панель не срабатывает
по достижении порога, а остаётся открытой. Действие всегда требует
отдельного нажатия — резкий случайный свайп никому не позвонит.

### Группировка: три режима вместо одного ✅

Раньше объединялись только подряд идущие вызовы. Добавлен режим, где все
вызовы абонента сливаются в одну карточку, и режим без группировки вовсе.

| Режим | Что делает | Когда полезен |
|---|---|---|
| **Подряд идущие** (по умолчанию) | Объединяет только соседние вызовы одного абонента | Журнал читается как хронологическая лента событий |

### Архитектура локализации: ноль хардкода

1. Скопировать `res/values/strings.xml` в `res/values-<code>/strings.xml`, перевести

## Изменения относительно v4.0 — интеграция с системным антиспамом

Разобрал тезис про «перенаправление вызова в системный/сторонний определитель».
Он содержит распространённую неточность, зато рядом лежат три настоящих
механизма, которые закрывают ту же задачу лучше. Все три реализованы.

### ❌ Что технически невозможно

**«Перенаправить входящий вызов на определитель Яндекса или Google».**
Публичного API для передачи вызова в чужой `CallScreeningService` не существует.
Нельзя и прочитать его вердикт — это внутреннее состояние другого приложения.

**«Запросить данные определителя из системного лога».**
В `CallLog.Calls` нет поля с рейтингом номера. Есть только `BLOCK_REASON` —
и то лишь постфактум, для уже заблокированных вызовов.

### ✅ Ключевой факт, который меняет архитектуру: ролей ДВЕ

| Роль | Кто держит | Когда срабатывает |
|---|---|---|
| `ROLE_DIALER` | Ogneliss | Управление вызовами, UI |
| `ROLE_CALL_SCREENING` | Яндекс, Kaspersky, Google — **или мы** | Фильтрация входящих |

Роли **независимы**. Порядок обработки входящего в AOSP:

1. Системный список блокировки — вызов не звонит вообще
2. `CallScreeningService` приложения с `ROLE_CALL_SCREENING`
3. `CallScreeningService` диалера по умолчанию (наш)

**Следствие, важное для позиционирования:** установка Ogneliss как телефона
по умолчанию **не отключает** Яндекс.Определитель. Он держит другую роль
и отрабатывает раньше нас. Пользователю не нужно выбирать между нами и им —
это снимает главное возражение против перехода на сторонний диалер.

Реализовано: `ScreeningRoleInfo` определяет обе роли, находит установленные
определители и умеет отдельно запросить `ROLE_CALL_SCREENING`.

### ✅ Механизм 1. Системный список блокировки (реализован)

`BlockedNumberContract` — общий с системой список. Доступен на запись **только**
приложению, выбранному телефоном по умолчанию.

Почему это лучше собственного блок-листа:
- блокировка происходит на уровне телефонии, телефон **вообще не звонит**;
  наш `CallScreeningService` срабатывает позже и на части прошивок успевает
  пропустить гудок — это ровно жалоба «блокировка работает не всегда»;
- список общий: номера, заблокированные в штатном «Телефоне», видны нам,
  и наоборот. Пользователь не теряет свои блокировки при переходе на Ogneliss;
- есть штатный системный экран управления (`createManageBlockedNumbersIntent`).

- [x] `SystemBlockRepository`: чтение, добавление, удаление, список
- [x] Проверка системного списка в нашем screening-сервисе

## ⚠️ Три расхождения с исходным анализом

### 1. «Версия 3.0: AI-расшифровка и резюме разговора» — технически невозможна

Расшифровка требует **аудиопотока разговора**. Он закрыт для сторонних
приложений с Android 10 ровно тем же ограничением, из-за которого мы отказались
от записи звонков. Нет записи — нет и расшифровки, резюме, перевода и поиска
по содержимому. Это не вопрос вычислительной мощности или качества модели.

Приложения, которые это обещают, обычно делают одно из:
- работают только на Android 9 и ниже;
- используют Accessibility Service — **прямой бан в Google Play**;
- подменяют звонок VoIP-мостом через свой сервер (номер и голос уходят третьей стороне);
- расшифровывают только **собственные** VoIP-звонки, а не сотовые.

Ни один вариант нам не подходит. **Пункт исключён из дорожной карты.**

Что реально можно дать взамен, и это закрывает исходную потребность
«не забыть, о чём договорились»:
- [ ] **Голосовая заметка после звонка** — пользователь сам наговаривает итог,
      запись идёт с микрофона по явному нажатию, хранится локально
- [ ] **Офлайн-распознавание этой заметки** в текст (`SpeechRecognizer`
      с `EXTRA_PREFER_OFFLINE`, на устройстве) → готовый текст в поле заметки
- [ ] Извлечение из заметки дат и сумм простыми правилами → предложение
      создать напоминание или событие

Это честно, работает офлайн и не нарушает ни политику Play, ни ст. 137 УК.

### 2. CardDAV, Exchange и Google Contacts sync конфликтуют с офлайн-принципом

Любая синхронизация требует `INTERNET`, а мы намеренно его не запрашиваем —
на этом построена вся аргументация Data Safety и доверие пользователя.

Решение: **синхронизация не нужна в принципе.** Android уже синхронизирует
контакты сам через системные аккаунты, а мы читаем `ContactsContract` —
то есть Google Contacts, Exchange и CardDAV-аккаунты **уже видны** приложению,
если настроены в системе. Дублировать эту работу вредно.

- [x] Контакты из всех системных аккаунтов доступны через ContactsContract
- [ ] Фильтр «показывать только контакты из аккаунта X»

### 3. SIP исключён

`android.net.sip` объявлен устаревшим в Android 12 и **удалён** в Android 14.
Собственная SIP-реализация — это отдельный продукт масштабом с сам диалер
(PJSIP, кодеки, NAT traversal, фоновая регистрация) и снова требует сети.
За рамками проекта. Пользователям SIP — Linphone или Zoiper.

## 🎯 Нефункциональные требования (из раздела «что раздражает»)

Разбор показал: самые частые причины удаления — не отсутствие функций,
а скорость, реклама и неудобный экран звонка. Перевожу это в измеримые
требования, которые проверяются до релиза.

| Жалоба | Требование | Как проверяем |
|---|---|---|
| Долго открывается | Холодный старт до интерактивности < 400 мс | Macrobenchmark, Baseline Profile |
| Задержка при наборе | Отклик клавиши < 16 мс, результат T9 < 50 мс | Индекс в Room, трассировка |
| Лаги списка | 0 пропущенных кадров на 5000 записей | Paging 3 + Macrobenchmark |
| Реклама и подписки | **Рекламы нет. Подписок нет.** | Архитектурное решение |
| Сложный интерфейс | Не более 3 экранов до любой функции | Ревью навигации |
| Трудно ответить/завершить | Кнопки ≥ 56 dp, разнесены ≥ 40 dp, без жестов по умолчанию | UI-тест, ручная проверка одной рукой |
| Случайные нажатия | Датчик приближения гасит экран | ✅ реализовано |
| Нельзя вернуться к разговору | Постоянное уведомление + плашка поверх окон | Частично: уведомление ✅ |
| Вылеты во время звонка | 0 крашей в сценариях телефонии | Стресс-тест, StrictMode |
| Спрятанные контакты | Контакты — вкладка первого уровня | ✅ реализовано |

### Отдельно про экран после звонка
В разборе он в списке желаемого, но в отзывах на аналоги это же
и раздражитель — всплывающее окно после каждого звонка бесит. Компромисс:

- по умолчанию показывается **только для номеров вне контактов**;
- закрывается сам, не блокирует возврат на домашний экран;
- полностью отключается одним переключателем;
- никогда не появляется поверх другого входящего вызова.

## 🔒 Принцип «данные не покидают устройство»

Не декларация, а проверяемое свойство сборки:

**Разрешение `android.permission.INTERNET` отсутствует в манифесте.**

Без него Android блокирует любое сетевое соединение на уровне ядра, независимо
от кода, транзитивных зависимостей и SDK. Следствия:

| Что даёт | Как |
|---|---|
| Гарантия для пользователя | Проверяется в свойствах APK за 5 секунд |
| Упрощение Data Safety в Play | «Данные не собираются и не передаются» — без оговорок |
| Защита от вредоносных зависимостей | Даже скомпрометированная библиотека не сможет ничего отправить |
| Соответствие 152-ФЗ | Нет трансграничной передачи, нет оператора ПД |

**Цена решения:** невозможны онлайн-базы спама, облачный бэкап и аналитика
сбоев (Crashlytics). Это осознанный размен. Если позже потребуется онлайн-определитель,
он выносится в **отдельный APK-флейвор** с явным экраном согласия — базовая
сборка остаётся полностью офлайновой.

**Дополнительно:**
- `allowBackup=false`, исключение из cloud-backup и device-transfer
- Блок-лист и настройки — в DataStore внутри приватного каталога приложения
- Планируется: шифрование блок-листа через AndroidKeyStore (этап 7)
