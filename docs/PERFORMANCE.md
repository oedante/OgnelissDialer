# Производительность

## Цели

Взяты из анализа отзывов на конкурентов: самые частые жалобы —
не отсутствие функций, а «долго открывается» и «лаги при наборе».
Функциональность у всех примерно одинаковая, скорость и есть
конкурентное преимущество.

| Метрика | Цель | Чем измеряется |
|---|---|---|
| Холодный старт до интерактивности | < 400 мс | `StartupTimingMetric` |
| Отклик клавиши | < 16 мс | Трассировка |
| Результат T9-поиска | < 50 мс | Room-индекс |
| Пропущенные кадры при прокрутке | 0 | `FrameTimingMetric` |

## Baseline Profile

Список методов, которые Android компилирует заранее (AOT) при установке
вместо интерпретации при первом запуске. Для приложения на Compose даёт
20–30 % к скорости холодного старта.

Для диалера это критичнее, чем для большинства приложений: его открывают,
когда нужно позвонить **прямо сейчас**.

```bash
# Сгенерировать профиль (нужно реальное устройство)
./gradlew :app:generateBaselineProfile
```

Результат попадает в `app/src/main/baseline-prof.txt` и **коммитится
в репозиторий**. Без него профиль не попадёт в сборку для пользователей.

### Что включать в профиль
Только первые секунды работы: запуск, журнал вызовов, клавиатура, набор.
Профиль не бесплатен — он увеличивает время установки и размер приложения.
Настройки и списки блокировки открывают редко, их включать не нужно.

## Замеры

```bash
# Холодный старт и прокрутка
./gradlew :benchmark:connectedBenchmarkAndroidTest
```

Только на **реальном устройстве**. Эмулятор даёт цифры, не имеющие
отношения к действительности: другая архитектура процессора, отсутствие
теплового троттлинга, иная работа планировщика.

Два теста старта — с профилем и без. Разница между ними и есть польза
от Baseline Profile; если её нет, профиль не применяется, и надо
разбираться почему.

## Кэширование: что кэшируется и что намеренно нет

Кэш — не бесплатное ускорение. Он занимает память и живёт своей жизнью,
поэтому каждое решение здесь обосновано отдельно.

| Что | Кэшируется | Почему так |
|---|---|---|
| Форматирование номеров | Да, 512 записей | libphonenumber разбирает строку и ищет регион в справочнике. Одни номера форматируются десятки раз |
| Готовые строки списка | Да, инкрементально | Подгрузка добавляет 150 записей, а пересобирался список из 3000 |
| Аватары в памяти | Да, 15 % памяти | Декодирование изображения — самая дорогая операция при отрисовке строки |
| Аватары на диске | **Нет** | Оригиналы уже лежат в провайдере контактов. Копировать их — занимать место ради данных, которые никуда не денутся |
| Список SIM | Да, до изменения | Binder-вызовы в системный процесс идут сотнями за секунду прокрутки |
| Журнал вызовов | **Нет** | Источник правды — системный провайдер. Своя копия разошлась бы с ним |

**Почему кэш номеров ограничен 512 записями.** Журнал грузится
страницами до трёх тысяч. Безразмерный кэш держал бы в памяти строки,
которые уже уехали за пределы экрана и не понадобятся. 512 покрывают
несколько экранов прокрутки в обе стороны; при переполнении вытесняется
самая давняя запись.

**Почему кэш аватаров ограничен 15 %.** Приложение должно уступать
память телефонии, когда идёт разговор. Отдавать больше означало бы
рисковать выгрузкой процесса в момент, когда он обязан работать.

## Подготовка строк: три уровня оптимизации

1. **Вынос из отрисовки.** Форматирование, подписи и описания для TalkBack
   считаются один раз при изменении данных, а не на каждом кадре.
   До этого на экране с десятью карточками при 60 кадрах получалось
   до шестисот разборов номера в секунду.

2. **Вынос из главного потока.** Подготовка идёт на `Default`.
   Раньше она выполнялась внутри `remember` в composable — то есть
   разбор трёх тысяч номеров происходил прямо во время отрисовки.

3. **Инкрементальность.** Строки, чьи данные не изменились,
   переиспользуются. Сравнивается целочисленный отпечаток входных
   данных: проверять «изменилось ли что-нибудь» через те же функции,
   что готовят строку, значило бы выполнить работу дважды,
   и оптимизация превратилась бы в замедление.

Плюс `contentType` у элементов списка: без него LazyColumn считает
соседние элементы потенциально разными и не переиспользует уже созданную
разметку — а это самая дорогая часть прокрутки.

## Стабильность типов — то, что перечёркивало остальное

### В чём была проблема

Compose делит типы на стабильные и нестабильные. Стабильные он
сравнивает и пропускает перерисовку, если ничего не изменилось.
**Нестабильные считаются изменившимися всегда.**

Класс нестабилен, если у него есть поле нестабильного типа. `List` —
интерфейс: за ним может стоять изменяемая реализация, и Compose
не может этого проверить. То же с лямбдами.

Ни одна модель не была помечена. Следствие: `CallLogGroup` содержит
`List<String>` → нестабилен → `CallLogRowState` содержит его →
нестабилен → **каждая строка списка перерисовывалась при любом
обновлении данных**, сколько бы мы ни кэшировали их подготовку.

То есть вся работа по подготовке строк заранее пропадала впустую.

### Что помечено

| Класс | Что делало нестабильным |
|---|---|
| `CallLogGroup`, `Contact` | `List` номеров |
| `NumberNote` | `List` меток |
| `UiState`, `SettingsState` | `List` и `Map` внутри |
| `CallLogFilter` | `Set` типов вызовов |
| `RevealAction` | лямбда `onClick` |

`RevealAction` — отдельный случай: список действий передаётся
в **каждую** строку журнала, и нестабильность одного элемента делала
весь список изменившимся при каждом кадре.

### Обещание нужно держать

`@Immutable` — это обещание компилятору, а не проверка. Если внутрь
попадёт изменяемый список и его кто-то поменяет, Compose об этом
не узнает и покажет устаревшие данные.

У нас списки создаются один раз при чтении из провайдера и заменяются
новыми объектами целиком — обещание выполнимо.

### Как проверить

```
./gradlew assembleRelease "-Pcompose.metrics=true"
```

Результат в `app/build/compose_metrics/`. Искать в `*-classes.txt`
строки `unstable class`, в `*-composables.txt` — `skippable: false`.

## Поиск

Поиск срабатывает на каждое нажатие цифры — чаще любой другой операции
в приложении. Три решения, каждое закрывает свою причину задержки.

### Выполнение в фоновом потоке

Раньше поиск шёл **синхронно в обработчике нажатия**: перебор всех
контактов, сопоставление по T9 для каждого имени и ранжирование
происходили между нажатием на цифру и её появлением на экране.
На тысяче контактов это десятки миллисекунд при бюджете 16 мс на кадр —
гарантированный пропуск кадров, который ощущается как «клавиатура
залипает».

Теперь поиск выполняется на `Default`, а поле ввода обновляется сразу
и синхронно: задержка в отображении самой цифры недопустима.

### Пауза 120 мс перед началом

Между цифрами при быстром наборе проходит 60–100 мс. Пауза склеивает их:
при наборе «495» поиск выполнится один раз вместо трёх. Два
промежуточных результата человек всё равно не успел бы прочитать.

Больше 120 мс — задержка становится заметной; меньше — склейки
не происходит.

### Отмена устаревшего поиска

Предыдущая задача отменяется при новом нажатии. Без этого результат
поиска по «5» мог прийти позже результата по «55» и перезаписать его —
человек увидел бы ответ на вопрос, которого больше нет.

Дополнительно результат сверяется с текущим запросом перед показом:
задача могла успеть завершиться до отмены.

### Кэш перевода имён в цифры

`toDigits` — посимвольный обход с поиском по таблице раскладки. Сам
по себе дёшев, но выполняется для **каждого** контакта на **каждую**
цифру: при тысяче контактов и наборе из пяти цифр это пять тысяч
переводов одних и тех же имён.

Кэш на 2048 записей покрывает большинство телефонных книг целиком.
Сбрасывается при смене языка: раскладка у разных алфавитов разная,
и старый кэш давал бы неверные совпадения.
