# Где что выполняется

Правило простое: **в главном потоке только отрисовка**. Всё, что
перебирает списки, разбирает строки или обращается к диску, уходит
в фон.

## Три диспетчера и когда какой

| Диспетчер | Для чего | Почему именно он |
|---|---|---|
| `Main` | Отрисовка, обновление состояния | Другого не дано |
| `IO` | Провайдеры Android, файлы, сеть | Пул растёт под ожидание: сто заблокированных потоков не вредят |
| `Default` | Группировка, поиск, форматирование | Пул по числу ядер: больше потоков не ускорит счёт, а переключения замедлят |

Частая ошибка — пускать счётную работу на `IO`. Она не сломается,
но пул раздуется без пользы, а переключения контекста съедят выигрыш.

## Что вынесено в фон и почему

### Загрузка данных

| Операция | Диспетчер | Стоимость |
|---|---|---|
| Чтение журнала | IO | Курсор провайдера |
| Чтение контактов | IO | Курсор провайдера |
| Список SIM | IO | Binder-вызовы в системный процесс |
| Room-запросы | Свой пул Room | Room уводит `suspend`-функции сам |

### Обработка после чтения

Это менее очевидная половина: **чтение уходило в фон, а обработка
прочитанного оставалась на главном потоке.**

| Операция | Что делает | На чём заметно |
|---|---|---|
| Группировка журнала | Перебор и склейка 3000 записей | Подгрузка во время прокрутки |
| Подготовка строк | Форматирование номеров, дат, подписей | То же |
| Разбивка по датам | Календарная группа для каждой записи | То же |
| Определитель номера | Разбор через libphonenumber | Открытие приложения |
| Статистика | Обход журнала с суммированием | Каждое обновление |
| Ярлыки | Сортировка журнала, обход контактов | Каждое обновление |

### Поиск

| Этап | Где | Пояснение |
|---|---|---|
| Обновление поля ввода | Main, синхронно | Задержка читалась бы как подвисание клавиатуры |
| Пауза 120 мс | — | Склеивает быстрый набор в один поиск |
| Сопоставление и ранжирование | Default | Перебор всех контактов и записей |
| Показ результата | Main | Только если запрос не изменился |

### Контакты

Фильтр, поиск по имени и разбивка по буквам — одним переходом
на `Default`. Три отдельных перехода дали бы три переключения потока
и три промежуточных состояния списка на экране.

## Чего НЕ выносим

**Отметку избранного, переключение SIM, установку фильтра.** Это запись
одного значения: переключение потока обойдётся дороже самой операции.

**Показ результата.** Обновление состояния Compose должно происходить
на главном потоке — иначе поведение непредсказуемо.

**Фильтрацию избранных** в контактах. Их единицы, проверка флага стоит
наносекунды.

## Ловушка: `viewModelScope` — это главный поток

```kotlin
viewModelScope.launch {
    heavyWork()          // ← в главном потоке!
}
```

`viewModelScope` использует `Dispatchers.Main.immediate`. Корутина
не означает фоновый поток: она означает возможность приостановиться.
Без явного `withContext` вся работа идёт там, где запущена.

Так же ведёт себя `remember` в Compose: он запоминает результат
между перерисовками, но вычисляет его в потоке композиции, то есть
в главном.

## Как проверить

`StrictMode` включён в debug и сообщает об обращениях к диску
из главного потока. Счётную работу он не ловит — её видно только
в профилировщике по синим столбикам.

Быстрая проверка: `adb shell dumpsys gfxinfo com.ogneliss.dialer` —
доля `Janky frames` должна быть ниже 5 %.
